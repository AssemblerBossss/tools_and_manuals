
### ISO DATE

Стандарт ISO Date — это международный стандарт написания даты и времени, установленный Международной организацией по стандартизации (ISO). Его официальное обозначение — ISO 8601.

Основная цель этого стандарта — устранить путаницу, которая возникает из-за разных национальных форматов дат (например, MM/DD/YYYY в США и DD.MM.YYYY во многих странах Европы).

#### Ключевые принципы формата ISO 8601:
1. Порядок от большего к меньшему: Сначала указывается самый крупный элемент (год), затем месяц, затем день.

- Формат: ГГГГ-ММ-ДД

- Пример: 2023-10-25

2. Использование 24-часового формата: Время указывается без AM/PM.

- Формат: чч:мм:сс

- Пример: 14:30:15 (полтретьего дня) или 23:45:00 (без четверти двенадцать ночи).

3. Разделитель между датой и временем — буква "T": Чтобы четко отделить дату от времени.

- Формат: ГГГГ-ММ-ДДTчч:мм:сс

- Пример: 2023-10-25T14:30:15

4. Указание часового пояса: В конце добавляется информация о временной зоне.

- По Всемирному координированному времени (UTC): Можно указать как Z (сокращение от "Zulu time").

  - Пример: 2023-10-25T14:30:15Z

- Смещение от UTC: Указывается как +чч:мм или -чч:мм.

  - Пример для Москвы (UTC+3): 2023-10-25T14:30:15+03:00

  - Пример для Нью-Йорка (UTC-4): 2023-10-25T14:30:15-04:00


### Точность даты/времени

В формате ISO 8601 нет жесткого ограничения на точность — стандарт позволяет указывать время с практически любой необходимой точностью, вплоть до долей секунды. Точность определяется количеством знаков после десятичного разделителя.

Уровни точности в ISO 8601:
1. Секунды (наименьшая стандартная единица)

- 2023-10-25T14:30:15Z

- 2023-10-25T14:30:15+03:00

2. Десятичные доли секунды

Стандарт позволяет добавлять десятичную дробь после секунд, используя точку (.) или запятую (,) как десятичный разделитель:

- Миллисекунды (3 знака):

  - 2023-10-25T14:30:15.250Z (250 миллисекунд)

- Микросекунды (6 знаков):

  - 2023-10-25T14:30:15.250123Z (250 миллисекунд 123 микросекунды)

Наносекунды (9 знаков):
  - 2023-10-25T14:30:15.250123456Z

3. Практические ограничения

Хотя стандарт теоретически позволяет бесконечную точность, на практике есть ограничения:

- Системные ограничения: Операционные системы и языки программирования имеют свои пределы

  - Windows: обычно 100 наносекунд

  - Unix-системы: микро- или наносекунды

  - JavaScript: миллисекунды

- Требования приложения: Большинству приложений достаточно:

  - Секунд (логирование, планирование)

  - Миллисекунд (веб-API, базы данных)

  - Микросекунд (высокочастотные транзакции)

### Формат хранения времени/даты в разных базах данных (самые популярные реляционные и нереляционные)

#### Реляционные (SQL) базы данных

#### 1. PostgreSQL

- TIMESTAMP - дата и время (с точностью до микросекунд)

```
TIMESTAMP '2023-10-25 14:30:15.123456'
```

- TIMESTAMPTZ - дата/время с часовым поясом

```
TIMESTAMPTZ '2023-10-25 14:30:15.123456+03'
```

- DATE - только дата

- TIME - только время

- INTERVAL - временной интервал

#### 2. MySQL

- DATETIME - дата и время (до микросекунд в версиях 5.6+)

```
'2023-10-25 14:30:15.123456'
```

- TIMESTAMP - Unix timestamp (4 байта, до 2038 года)

- DATE - только дата

- TIME - только время

#### 3. SQL Server

- DATETIME2 - рекомендованный тип (точность до 100 наносекунд)

```
'2023-10-25 14:30:15.1234567'
```

- DATETIME - устаревший (точность ~3.33 мс)

- DATETIMEOFFSET - с часовым поясом

- DATE, TIME - отдельные типы

#### 4. Oracle

- DATE - дата и время (до секунд)

- TIMESTAMP - с дробными секундами

```
TIMESTAMP '2023-10-25 14:30:15.123456'
```

- TIMESTAMP WITH TIME ZONE - с часовым поясом

- INTERVAL - временные интервалы

#### Нереляционные (NoSQL) базы данных

#### 1. MongoDB

- BSON Date - 64-битное число (миллисекунды с Unix epoch)

```
ISODate("2023-10-25T14:30:15.123Z")
// Хранится как NumberLong("1698244215123")
```

#### 2. Redis

- Unix timestamp (секунды или миллисекунды)

- Строковый формат ISO 8601

- Внутреннее представление: обычно строки или числа

#### 3. Cassandra

- timestamp - 64-битное число (миллисекунды с Unix epoch)

- date - только дата (дни с Unix epoch)

- time - только время (наносекунды с полуночи)

#### 4. Elasticsearch

- Строковый формат ISO 8601

```
"2023-10-25T14:30:15.123Z"
"2023-10-25T14:30:15+03:00"
```

### Какие типы хранят дату точнее (кроме string)

| Тип данных | СУБД | Максимальная точность | Размер | Рекомендация |
|------------|------|----------------------|--------|--------------|
| TIMESTAMP | Oracle | Наносекунды (9 знаков) | 11 байт | Для научных данных |
| DATETIME2 | SQL Server | 100 наносекунд (7 знаков) | 6-8 байт | Высокая точность + эффективность |
| TIMESTAMPTZ | PostgreSQL | Микросекунды (6 знаков) | 10 байт | Лучший баланс |
| DATETIME | MySQL | Микросекунды (6 знаков) | 5-8 байт | Для современных приложений |
| BSON Date | MongoDB | Миллисекунды | 8 байт | Для документных БД |
| TIMESTAMP | MySQL | Микросекунды | 4-7 байт |  |
| DATE | Oracle | Секунды | 7 байт | Базовая точность |
| DATETIME | SQL Server | ~3.33 мс | 8 байт | Не рекомендуется |

### Какая точность времени у спутников

#### Навигационные спутники (GPS, ГЛОНАСС, Galileo, BeiDou)

##### Атомные часы на борту
- Тип часов: Рубидиевые (Rb) и цезиевые (Cs) атомные часы

- Точность бортовых часов:

  - Цезиевые: ≈ 1-2 наносекунды/день

  - Рубидиевые: ≈ 5-10 наносекунд/день

| Система | Точность позиционирования | Точность времени |
|---------|---------------------------|------------------|
| GPS | 3-5 метров | ~10-30 наносекунд |
| ГЛОНАСС | 5-10 метров | ~20-50 наносекунд |
| Galileo | 1-3 метра | ~5-20 наносекунд |
| BeiDou | 3-5 метров | ~10-30 наносекунд |

#### Геостационарные спутники связи
- Точность синхронизации: 1-100 микросекунд

- Используют: Кварцевые генераторы + коррекция с Земли

- Назначение: Синхронизация сетей связи, телевещание

#### Спутники дистанционного зондирования Земли
- Требуемая точность: 1-100 микросекунд

- Для: Синхронизации данных с разных датчиков

- Пример: Спутники Landsat, Sentinel

#### Научные спутники

##### Спутники для фундаментальной физики

- GRACE Follow-On: наносекундная точность для измерений гравитации

- LISA Pathfinder (гравитационные волны): пикосекундная точность

#### Спутники системы UTC

- Участвуют в формировании всемирного координированного времени

- Точность сравнения часов: 0.1-1 наносекунда

### Какая задержка у 5g

#### Целевые показатели задержки в 5G

| Сценарий использования | Целевая задержка | Реальная задержка |
|------------------------|------------------|-------------------|
| eMBB (улучшенный мобильный широкополосный доступ) | 10-30 мс | 20-40 мс |
| URLLC (сверхнадежная связь с низкой задержкой) | 1 мс | 5-10 мс |
| mMTC (массовый IoT) | 10-100 мс | 50-100 мс |

#### Фактическая задержка в развернутых сетях 5G

- Средняя задержка (RTT): 10-30 мс (в идеальных условиях)

- Лучшие случаи: 5-8 мс (в лабораторных условиях)

- Реальные городские условия: 15-40 мс

## Подключение с определенного IP

```bash
sudo nano /etc/mongod.conf
```

В bindIP добавляем адрес нашей машины, чтобы mongo слушала с этого адреса

```bash
sudo systemctl restart mongod
```

Далее фаервол

```bash
sudo ufw enable

sudo ufw allow from <IP>

# запрещаем все на этом порту
sudo ufw deny 27017
```

Чтобы просмотреть правила фаервола

```bash
sudo ufw status numbered
```

Чтобы удалить 

```bash
sudo ufw delete <номер_deny_правила>
```

или все

```bash
sudo ufw reset
```

Чтобы подключиться

```bash
sudo mongosh --host 192.168.107.130 --port 27017
```

## Общий пользователь - общий пароль

### 1. Запуск с docker
```bash
docker run -d --name mongodb -p 27017:27017 \
  -e MONGO_INITDB_ROOT_USERNAME=commonuser \
  -e MONGO_INITDB_ROOT_PASSWORD=commonpassword123 \
  mongo:latest
```

### 2. Не в докере

```javascript
use admin
db.createUser({
  user: "commonuser",
  pwd: "commonpassword123",
  roles: ["root"]
})
```

Меняем конфигурационный файл
```yaml
#mongod.conf:
security:
  authorization: enabled

systemLog:
  destination: file
  path: /var/log/mongodb/mongod.log
  logAppend: true

net:
  port: 27017
  bindIp: 0.0.0.0

storage:
  dbPath: /data/db

# Подключения с localhost не требуют аутентификации
setParameter:
  enableLocalhostAuthBypass: false
```

Перезапустить службу
```bash
sudo systemctl restart mongod
```


## Несколько пользователей - разные пароли

### 1. Сначала заходишь в админку и создаёшь пацанов:

```javascript
use admin

// Первый пользователь - для основного приложения
db.createUser({
  user: "app_user",
  pwd: "app_password_123",
  roles: [
    { role: "readWrite", db: "myapp" },
    { role: "read", db: "analytics" }
  ]
})

// Второй пользователь - только для чтения (для отчетов)
db.createUser({
  user: "report_user", 
  pwd: "report_password_456",
  roles: [
    { role: "read", db: "myapp" },
    { role: "read", db: "analytics" }
  ]
})

// Третий пользователь - админ базы
db.createUser({
  user: "db_admin",
  pwd: "admin_password_789", 
  roles: [
    { role: "dbAdmin", db: "myapp" },
    { role: "dbAdmin", db: "analytics" },
    { role: "userAdmin", db: "myapp" }
  ]
})
```

### 2. Каждый мудак подключается со своим паролем:

```bash
#Обычный шнырь
mongodb://app_user:app_password_123@localhost:27017/myapp

# Отчеты:
mongodb://report_user:report_password_456@localhost:27017/myapp

# Админ:
mongodb://db_admin:admin_password_789@localhost:27017/myapp
```

## Роли и права (чтобы не было беспредела)

- `read` - только смотреть, руки похуй
- `readWrite` - и смотреть, и изменять
- `dbAdmin` - админить базу (индексы, статистика)
- `userAdmin` - управлять пользователями
- `clusterAdmin` - права на весь кластер
