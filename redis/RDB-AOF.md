# 📚 Redis Persistence: RDB и AOF

Redis по умолчанию работает как **in-memory** база данных, т.е. все данные хранятся в оперативной памяти.  
Чтобы данные не терялись при перезапуске сервера или сбое, Redis поддерживает два механизма персистентности:

- **RDB (Redis Database File)** — снимки состояния данных (снепшоты).
- **AOF (Append Only File)** — журнал операций.

---

## 🟢 RDB (Redis Database File)

### 🧐 Определение

**RDB** — это механизм сохранения снимков (snapshots) всех данных, находящихся в памяти Redis, на диск в бинарном формате.

- Сохраняется **полное состояние базы данных** на определённый момент времени.
- Результат — бинарный файл `dump.rdb`.

### ⚙️ Конфигурация

```conf
save <time_in_seconds> <num_operations>
```

Примеры:

```bash
save 900 1      # Сохранять, если за 900 секунд изменился хотя бы 1 ключ
save 300 10     # Сохранять, если за 300 секунд было 10 изменений
save 60 10000   # Сохранять, если за 60 секунд было 10000 изменений
```

### ✅ Плюсы RDB

- Компактный формат, удобно хранить бэкапы.
- Быстрая загрузка при старте Redis.
- Подходит для disaster recovery (восстановления после сбоев).

### ❌ Минусы RDB

- Данные между снимками могут потеряться.
- Создание снимков занимает ресурсы процессора и памяти.


## 🔴 AOF (Append Only File)

### 🧐 Определение

**AOF** — это механизм записи всех операций Redis в лог-файл.
При перезапуске Redis файл воспроизводится и база восстанавливается.

Файл по умолчанию называется **appendonly.aof**

### ⚙️ Конфигурация

Включение AOF:

```bash
appendonly yes
```

### Режимы синхронизации (частота записи на диск):

```bash
appendfsync no         # Никогда не форсировать запись (надежность низкая, но быстро)
appendfsync always     # Форсировать запись после каждой команды (очень надежно, но медленно)
appendfsync everysec   # Записывать каждую секунду (баланс скорость/надежность)
```

### ✅ Плюсы AOF

- Более надежная персистентность (можно потерять максимум 1 секунду данных).
- Легче читать и редактировать (текстовый формат команд Redis).
- Можно восстановить данные, проиграв журнал.

### ❌ Минусы AOF

- Файл обычно больше, чем dump.rdb.
- Восстановление занимает больше времени, чем при RDB.
- Чуть ниже производительность.

## ⚖️ Сравнение RDB и AOF

| Характеристика              | RDB (снепшоты)                 |AOF (журнал операций) |
| ----------------------------| -------------------------------|-------------------------|
| **Формат**                  | Бинарный файл                  | Текстовый лог команд |
| **Надёжность**              | Потеря данных между снапшотами | Почти полная сохранность |
| **Скорость восстановления** | Быстрая                        | Медленнее |
| **Размер файла**            | Компактный                     | Обычно больше |
| **Подходит для**            | Бэкапы и репликации            | Высокой надежности данных |


### 💡 Рекомендации по использованию

- Использовать **RDB** для регулярных бэкапов.
- Использовать **AOF** для надёжности (минимизации потерь данных).

В продакшене часто включают оба механизма одновременно:

```bash
save 900 1
save 300 10
appendonly yes
appendfsync everysec
```


Так достигается баланс между скоростью и надежностью.
